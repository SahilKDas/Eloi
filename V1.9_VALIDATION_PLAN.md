# Eloi v1.9 NNUE and final-gauntlet plan

Status: designed, not yet executed.

This plan decides between 64- and 128-hidden-unit NNUE candidates and then
runs Eloi's fixed 250-game release gate against the official v1.5.0-beta.1
baseline. Training, architecture selection, and the release gauntlet are three
separate decisions; passing an earlier stage does not waive a later one.

## Fixed rules

- Use one source commit, one pair of input files, one deterministic split, and
  identical training parameters for both architectures.
- Keep the NNUE temporary directory at or below 7 GiB. Do not download a full
  Lichess database onto this computer merely to obtain the bounded samples.
- Never commit raw training inputs, candidate executables, checkpoints, PGNs,
  or temporary model files.
- Record SHA-256 hashes for the two inputs, both generated headers, both
  candidate executables, the opening suite, and the official baseline.
- Use exactly three engine threads, 32 MiB hash, books disabled, Standard
  chess, equal 250 ms/move, and mirrored colors for all architecture and final
  matches.
- Do not run GUI or Lichess processes during timed comparisons. The harness
  may run exactly the two UCI engine processes it needs.
- Never publish a candidate that fails correctness, reproducibility, or the
  final strength gate, regardless of a favorable watched game.

## Stage 0: make the trainer comparison trustworthy

Before real training, correct and test these reproducibility details in
`scripts/train_nnue.py`:

1. Give each architecture an independent copy or immutable ordering of every
   training list. The current loop shuffles shared lists while training 64,
   which can change the order subsequently observed by 128.
2. Add a regression test proving that a combined `--architectures 64 128` run
   produces the same per-architecture metrics and headers as separate 64-only
   and 128-only runs from the same miniature fixture.
3. Record the Python, NumPy, and python-chess versions in provenance alongside
   the existing seed, parameters, counts, input hashes, and output hash.
4. Make candidate selection report-only when comparing both architectures.
   Neither candidate may overwrite the tracked production headers until the
   later engine-level playoff chooses a winner.
5. Re-run the existing miniature end-to-end trainer smoke test and verify that
   failed/staged candidates are removed and the 7 GiB hard limit still works.

No full dataset run starts until all five checks pass.

## Stage 1: acquire and freeze bounded inputs

Use the dated CC0 Lichess puzzle CSV and evaluation JSONL samples described in
`DATA_SOURCES.md`. If those exact compact samples cannot be recovered, produce
new deterministic bounded samples by streaming the official sources on
another machine or external storage; do not retain the full databases here.

Preflight evidence must contain:

- source URLs or upstream identifiers, dates, licenses, and retrieval method;
- byte sizes and SHA-256 hashes of both compact input files;
- the deterministic sampling command and seed, if new samples were made;
- at least 12,000 usable puzzle pairs and 12,000 usable evaluated positions;
- both kings and a legal Standard position in every accepted record;
- a dry-run storage estimate that keeps temporary data at or below 7 GiB.

Place inputs under ignored `.deps/nnue-inputs/` or on an explicitly named
external path. After their hashes are recorded, make them read-only for the
duration of the experiment.

## Stage 2: train 64 and 128 independently

Use the same interpreter and identical arguments for both runs. Write every
output below ignored `tmp/nnue-training/`; do not touch production headers.

```powershell
$python = '.\.deps\lichess-bot\.venv\Scripts\python.exe'
$puzzles = '.\.deps\nnue-inputs\lichess-puzzles.csv'
$evaluations = '.\.deps\nnue-inputs\lichess-evaluations.jsonl'

& $python .\scripts\train_nnue.py `
  --puzzles $puzzles --evaluations $evaluations `
  --architectures 64 --limit 12000 --eval-limit 12000 --epochs 3 `
  --validation-fraction 0.1 --max-temp-gb 7 `
  --temp-dir .\tmp\nnue-training\work-64 `
  --output .\tmp\nnue-training\candidate-64\nnue_weights.hpp `
  --architecture-output .\tmp\nnue-training\candidate-64\nnue_architecture.hpp `
  --provenance .\tmp\nnue-training\candidate-64\provenance.json

& $python .\scripts\train_nnue.py `
  --puzzles $puzzles --evaluations $evaluations `
  --architectures 128 --limit 12000 --eval-limit 12000 --epochs 3 `
  --validation-fraction 0.1 --max-temp-gb 7 `
  --temp-dir .\tmp\nnue-training\work-128 `
  --output .\tmp\nnue-training\candidate-128\nnue_weights.hpp `
  --architecture-output .\tmp\nnue-training\candidate-128\nnue_architecture.hpp `
  --provenance .\tmp\nnue-training\candidate-128\provenance.json
```

Repeat each run once into a second temporary directory. The repeated header
and provenance-content hashes must match after excluding only path fields. A
mismatch stops the experiment.

Offline qualification is not the final selection. Record evaluation MAE and
tactical ranking accuracy for both architectures. Reject a candidate if its
metrics are missing, its quantized header is malformed, or it regresses from
the current production network by more than 5 cp MAE or 0.5 percentage points
of tactical accuracy without a clearly documented engine-level benefit.

## Stage 3: build two otherwise-identical engines

Starting from the same clean source commit, install one candidate's two
generated headers, build it in a dedicated directory, and copy only the
resulting executable and its hashes into ignored `tmp/nnue-playoff/`. Restore
the tracked headers before repeating for the other architecture. The only
source differences between the two builds must be:

- `include/eloi/nnue_weights.hpp`; and
- `include/eloi/nnue_architecture.hpp`.

For each executable run:

```powershell
ctest --test-dir <candidate-build> --output-on-failure
<candidate-exe> --perft --depth 4
<candidate-exe> --bench --depth 6
& '.\.deps\lichess-bot\.venv\Scripts\python.exe' `
  '.\scripts\differential_movegen.py' `
  --engine '<candidate-exe>' --samples 32
```

Also run the shallow speed suite against the current production candidate.
Record depth-1/5/10 medians and NNUE throughput. A 128-unit candidate that does
not demonstrate a strength benefit may not displace 64 merely because its
offline metric is fractionally higher.

## Stage 4: architecture playoff

Run a fixed 250-game, 125-opening mirrored playoff between the 64- and
128-unit executables with the same conditions as the final gate. Use separate
checkpoint, PGN, JSON, and Markdown paths from the final gauntlet. Do not stop
early based on favorable interim results.

Selection rule:

- select 128 if it scores at least 55% in the playoff and passes every
  correctness/offline gate;
- select 64 if 128 scores at most 45%;
- between 45% and 55%, treat the result as inconclusive and select 64 because
  it is smaller and faster unless 128 has a separately reproduced tactical
  correction that justifies another preregistered test.

This playoff selects the architecture only. It does not count toward the final
release gate.

## Stage 5: install and reproduce the selected NNUE

Copy the selected generated weights and architecture into the tracked include
directory and write `data/nnue_provenance.json`. Review the diff to ensure no
other playing logic changed. Then run:

```powershell
powershell -ExecutionPolicy Bypass `
  -File .\scripts\verify-reproducible.ps1 -StageRelease
```

Two clean builds must be byte-for-byte identical. Freeze the staged candidate
SHA-256 before starting the final gauntlet; changing any source, compiler
input, config, or binary invalidates the checkpoint and requires a new run.

## Stage 6: 250-game final gauntlet

Baseline requirements:

- executable: official `v1.5.0-beta.1` Windows x64 Eloi;
- required SHA-256:
  `614CE6D601AFC749EA4EFD8FC94A8BAE79EF4537374B0984E292A92CA0A99B7F`;
- suite: `data/strength_openings.json`, with its hash recorded;
- candidate: the byte-reproducible selected-NNUE executable from Stage 5.

Before starting, connect the computer to AC power, prevent sleep, close heavy
background workloads, confirm zero GUI/Lichess Eloi processes, and preserve at
least the ignored checkpoint directory. The harness launches only two UCI
processes and resumes only when every identity field still matches.

```powershell
& '.\.deps\lichess-bot\.venv\Scripts\python.exe' `
  '.\scripts\engine_lab.py' `
  --candidate '.\dist\release\Eloi.exe' `
  --baseline '.\tmp\engine-lab\beta1\Eloi.exe' `
  strength `
  --suite '.\data\strength_openings.json' `
  --checkpoint '.\tmp\engine-lab\v1.9-final-strength.json' `
  --pgn '.\tmp\engine-lab\v1.9-final-strength.pgn' `
  --games 250 --movetime-ms 250 --max-plies 200 `
  --required-win-rate 0.60
```

The pass condition is fixed: all 250 games completed and at least 150 raw
candidate wins. Draws do not count as wins. Report W/D/L, raw win rate, score,
estimated Elo difference, all hashes, start/finish times, and any interruption.
There is no rounding waiver and no substitution of the earlier 40-game sample.

## Stage 7: decision and cleanup

On a pass:

1. Run the complete correctness suite, final speed/deep reports, two-build
   reproducibility proof, both golden package builds, and Defender scans.
2. Confirm `dist/artifacts` contains exactly the standalone ZIP and the
   Exoskeleton ZIP.
3. Attach the final JSON, Markdown, and PGN evidence to the release; do not add
   binaries or large evidence files to Git.
4. Commit only the selected NNUE headers, provenance, required documentation,
   tests, and source changes.

On a failure, do not publish the RC as strength-qualified. Preserve the hashed
report, restore the previous production NNUE, and diagnose before preregistering
a different experiment. Do not tune against the failed 250-game suite and then
reuse it as if it were unseen evidence.

After either outcome, remove unsuccessful candidate builds, repeat-training
directories, and copied inputs that are no longer needed. Retain only compact
provenance and release evidence; verify the cleanup target is inside ignored
`tmp/` or `.deps/` before deleting it.
